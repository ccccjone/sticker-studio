# 项目初始化

kit 只规定**流程**（分级、plan、测试先行、验收门、复盘），不规定语言、框架或架构。
这些由每个项目在这里决定，记录为 ADR，之后才被当作约束。

## 判断是否需要

满足任一就执行：`.claude/verify.sh` 仍含 `UNCONFIGURED`；CLAUDE.md「项目特定」段仍是占位符；仓库里还没有任何源代码。

**已有代码的仓库**：不重新选型。派 `explorer` 读清单文件（依赖、构建、测试配置）和目录结构，把现状写成 ADR 0001（"记录现状"），再做第 3 步；对现状有疑问才问用户。

## 1. 了解项目（按 S2 处理：先问，确认后再动手）

一次集中问，只问会改变选型的问题，用户已经说明的不再问：

- 做什么、给谁用、运行在哪（iOS / web / 服务端 / CLI / 多端）
- 已有偏好或必须沿用的东西（语言、框架、后端服务、既有代码库）
- 规模与寿命（原型验证 / 长期维护产品）
- 硬约束（离线、隐私、成本、上架审核、部署环境）

## 2. 提出选型

给出 1 个推荐 + 1-2 个备选，每个说明取舍。不要默认套用任何固定栈；用户明确指定时直接采用。
覆盖：语言与框架、目录结构、测试框架、lint / 格式化 / 类型检查工具、UI 视觉验证方式（如适用）。

用户确认后写 `docs/02-Architecture/Decisions/0001-tech-stack.md`（ADR 格式见 Doc-Conventions.md）。
架构分层等较大决定可另写 0002 等；原型项目可以只写一份简短 ADR。

## 3. 把决定落进 kit

| 文件 | 写什么 |
|---|---|
| `.claude/verify.sh` | 删掉 `UNCONFIGURED` 两行，写入 lint / 类型检查 / 测试命令；确认在空项目脚手架上能通过 |
| `CLAUDE.md`「项目特定」段 | 技术栈一句话、目录约定、运行 / 测试命令、UI 截图方式、引用 ADR 0001 |
| `.claude/settings.json` | 仅追加本项目特有的危险命令到 `ask` / `deny`（例如数据库重置、生产部署） |
| git pre-commit | `exec .claude/verify.sh` |

目录约定只写到 CLAUDE.md，不改 kit 的 skills 和 agents——它们保持栈无关。

## 4. 脚手架

作为第一个 S1 走正常流程：spec（最小可运行骨架 + 1 个冒烟测试）→ plan → 执行 → verify.sh 全绿 → 首个 commit。

## 5. 之后改选型

技术栈或架构变化时，新写一份 ADR 标注 `Superseded by`，并同步更新 CLAUDE.md「项目特定」段和 verify.sh。
