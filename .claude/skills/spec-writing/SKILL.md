# Spec 分级与写作

目标：问得太少会返工，问得太多会打扰。先分级，再决定澄清和文档的力度。

## 1. 分级（先做，写在回复第一行）

| 级别 | 触发条件（满足任一即取更高级） | 要求 |
|---|---|---|
| **S0** | 1-2 文件、容易撤销、无数据/权限/接口变化（typo、文案、样式微调、配置） | 不写 spec。回复中用 1-3 句说明假设，直接做 |
| **S1** | 普通 feature / 非 trivial bug，影响范围清楚 | 短 spec（≤60 行）：目标、非目标、验收标准、假设 |
| **S2** | 数据 schema / 迁移、认证与权限（含数据库行级权限）、支付与订阅、公开 API、跨模块架构、不可逆操作 | 完整 spec（200-400 行上限，写够即可）+ 用户确认后才进 plan |

拿不准时取高一级，但在回复里说明理由，让用户可以一句话降级。

## 2. 澄清问题

- 只问**会改变方案**的问题，一次集中问完，S1 不超过 3 个，S2 不超过 6 个。
- 能从代码库、现有 spec、ADR 里查到的不要问（先派 explorer 查）。
- 对不问的部分，写成"假设"列在 spec 里，用户确认 spec 时一并确认。

## 3. Spec 模板

```markdown
# <Feature 名>

> **状态**：草案 v1 | 已批准
> **级别**：S1 | S2
> **日期**：YYYY-MM-DD

## 目标
## 非目标
## 假设（未经确认，用户批准 spec 即视为确认）
## 行为与验收标准   ← 每条可测试；UI 类写清截图应呈现什么
## 数据流 / 错误处理   ← S2 必填
## 风险与回滚   ← S2 必填
## 待决问题
```

文件名：`docs/03-Specs/YYYY-MM-DD-<kebab-topic>.md`。S1/S2 批准后调用 plan-execution skill 写 plan。
