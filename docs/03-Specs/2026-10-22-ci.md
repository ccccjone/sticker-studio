# CI：GitHub Actions 验收门

> **状态**：草案 v1
> **级别**：S1
> **日期**：2026-10-22
> **Backlog**：A2

## 目标

push 到 `main` 和所有 PR 自动跑与本地相同的验收门，让"三件套全绿"不再靠自觉；为 A1 部署提供"CI 通过后才部署"的前置 job。

## 非目标

- 不做部署（A1 单独 spec，复用本 workflow 的 job）。
- 不做 E2E / Playwright（verify skill 仍是本地手动配方；进 CI 另议）。
- 不做覆盖率门槛、矩阵多 Node 版本、依赖缓存以外的加速。

## 假设

- Node 22（本地 v22.19，Vite 8 要求 `^20.19 || >=22.12`）。
- 公开仓库的 Actions 分钟数免费；私有仓库也在免费额度内。
- CI 直接调用 `.claude/verify.sh`，保持"验收命令单一来源"（CLAUDE.md 硬规则 4）；verify.sh 不依赖 Claude Code 环境。
- 额外跑一次 `npm run build`：verify.sh 不含 vite 构建，而构建失败只有部署时才暴露。

## 行为与验收标准

1. 新增 `.github/workflows/ci.yml`，触发：`push` 到 `main`、`pull_request`、手动 `workflow_dispatch`。
2. job `verify`：checkout → setup-node 22（npm 缓存）→ `npm ci` → `.claude/verify.sh` → `npm run build`。
3. 同一分支的新 push 取消旧的进行中运行（`concurrency` + `cancel-in-progress`）。
4. 最小权限：`permissions: contents: read`。
5. 验收证据：push 后 `gh run watch` / `gh run view` 显示 `verify` 成功，日志中可见 `Tests 173 passed`（或当时实际数）。
6. 负向证据：在临时分支上故意制造 lint 失败的 PR/push，CI 变红；随后删除该分支。

## 测试策略

workflow 是配置，无法写单元测试；以"真实运行一次成功 + 一次故意失败"作为红/绿证据（替代红测试，在 plan 中注明）。
